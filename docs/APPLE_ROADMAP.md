# Apple platform foundation

The macOS host, embedded packet-tunnel target, typed Libbox adapter, real native traffic-counter bridge and exact session-identity restoration are implemented. This remains a development candidate, not a verified working macOS VPN release. `HoneyProxyCoreReady` stays false in the source and ordinary preview/release builds remain unavailable. A separate local Debug path requires the explicit `HONEYPROXY_DEVELOPMENT_VPN` compilation flag and valid Apple-anchored development signatures on both host and provider, with a matching team and Network Extension/App Group entitlements. No VPN profile is created by initialization, and no administrator subprocess is used. Real signed routing tests have not yet been performed.

## Distribution and account gates

The first package targets the Mac App Store with an embedded `.appex`. Apple limits this macOS packet-provider packaging to App Store distribution. A standalone Developer ID release instead needs a separate system-extension target, activation flow, signing and notarization; changing the host certificate alone is insufficient. [Apple TN3134](https://developer.apple.com/documentation/technotes/tn3134-network-extension-provider-deployment).

Apps offering VPN services on the App Store must use Apple's VPN APIs and be offered by an organization enrolled in the Apple Developer Program. This publication rule is distinct from local testing: a paid Individual team can provision Network Extension development builds, while a free Personal Team cannot. A paid team and local signing resources have not been prepared on this Mac. [App Review Guidelines 5.4](https://developer.apple.com/app-store/review/guidelines/#vpn-apps), [Apple DTS on Individual teams](https://developer.apple.com/forums/thread/815456), [Personal Team limitation](https://developer.apple.com/forums/thread/128767).

Register the host identifier `ru.honeyvpn.proxy.macos`, provider identifier `ru.honeyvpn.proxy.macos.PacketTunnel`, and shared application group `group.ru.honeyvpn.proxy` under the selected team before signed device testing. Both targets require matching Network Extension and app-group entitlements. The local full Xcode license remains unaccepted; this task does not accept it automatically.

## Native bridge

`ru.honeyvpn.proxy/apple_vpn` provides `initialize`, `requestPermission`, `start(config, profileId, sessionId)`, `stop`, `checkStatus`, and `getStatus`. The caller supplies a positive profile ID and a fresh UUID session ID; the host and provider preserve that identity rather than generating an unrelated one. `ru.honeyvpn.proxy/apple_vpn_status` emits OS-observed connection events. A successful start request does not imply `CONNECTED`; only `NEVPNStatus.connected` does. Stop waits for OS confirmation, with a ten-second timeout that reports an error rather than falsely announcing disconnection.

The host selects only its own provider profile. Configurations and copied local geo rules are staged in the signed app-group container with restricted file permissions. Session configuration is published atomically and exclusively with mode `0600`; UUID collisions and existing symlinks are never overwritten. The provider retains only its validated UUID session URL and deletes that file on failed startup/stop, including after UI relaunch. The host purges orphan UUID sessions older than 24 hours only after every owned profile is OS-confirmed disconnected/invalid; it protects fresh staged files, active configurations, symlinks and unrelated assets. Baseline status snapshots do not remove an in-flight configuration. Closing the UI does not stop an OS-managed tunnel.

Provider messages carry bounded status, real Libbox upload/download totals, counter availability and the validated profile/session identity. Rates are derived only from valid counter samples; unavailable rates remain unavailable rather than becoming synthetic zero. A measured zero is displayed as zero. Status remains OS-authoritative, and stale or mismatched session replies cannot overwrite a newer connection.

After UI relaunch, read-only native discovery completes before a new connection can start. The Dart bridge restores the native profile/session IDs and maps the active profile to the stored configuration only when that identity matches. It does not substitute the saved selection for an unknown native profile. Unknown profiles are labelled as unknown, including retained errors after an unconfirmed stop. Cleanup of a rejected or unsubmitted new start does not stop another OS-managed session. These code paths still require signed-device traffic and crash/reopen QA.

## Core build and runtime

The verified source pin is `shtorm-7/sing-box-extended` commit `a47bdbe2aefc4da0aa8dd2280fb54c429dd0bfe0`, tag `v1.13.12-extended-2.1.2`. The source revision, toolchain and features are selected in `core-lock.json`; Apple preparation/staging/development scripts read that same manifest. The release contains CLI binaries for Darwin, not a ready-made `Libbox.xcframework`. The pinned source requires Go 1.26.1; CI uses patched Go 1.26.8 and gomobile/gobind v0.1.12.

This is the newest reviewed release preserving the existing WireGuard/WARP peer `reserved` bytes. `v1.13.12-extended-2.1.3` and later, including `v1.14.1-extended-2.7.2`, remove that field; 1.14 also removes the Windows generator's existing legacy DNS schema. They cannot replace the current core without a deliberate compatibility migration. The newer Amnezia header-protection/range fields are separate from `reserved` and do not restore that WARP behavior. Android's external tun2socks is updated independently to 2.7.0; the Apple packet provider uses the real Libbox TUN and does not launch tun2socks. [Selected peer schema](https://github.com/shtorm-7/sing-box-extended/blob/a47bdbe2aefc4da0aa8dd2280fb54c429dd0bfe0/option/wireguard.go), [1.14 peer schema](https://github.com/shtorm-7/sing-box-extended/blob/55faa763f986f4ca8a492d9b2719bc6330d2bef5/option/wireguard.go).

The selected Amnezia schema includes `I1`–`I5`, `J1`–`J3`, `itime`, `S1`–`S4` and `H1`–`H4` ranges. It does not expose the newer `header_protection_key`, `content_padding_addition`, `rekey_after_time`, `rekey_timeout`, `reject_after_time`, `keepalive_timeout` or `max_handshake_attempts` fields. Configurations requiring those AmneziaWG 3.1 options are outside this validated core's capabilities; this update does not claim full 3.1 support.

The separate framework workflow builds unsigned macOS slices and generated Objective-C headers. Its asserted source patch retains gVisor, QUIC, WireGuard/AWG, uTLS and Clash API support; it omits Naive/Cronet and unrelated features. Provenance and output checksum accompany the artifact. The same job stages the verified static framework, compiles the full universal provider with its real adapter, and checks linked symbols. Its app artifact is `macOS-core-preview-VPN-unavailable`; this does not enable VPN readiness.

The pinned integration uses `LibboxSetupOptions`, `LibboxNewCommandServer`, and `startOrReloadService`, together with a `LibboxPlatformInterfaceProtocol` implementation. `openTun` must install real `NEPacketTunnelNetworkSettings` and return the extension's real utun descriptor; the Go wrapper duplicates that descriptor and owns the duplicate. Avoid invented descriptors, subprocess TUN access, and copying current SFA signatures without checking the pinned generated header. The pinned DNS method returns one `StringBox`; newer upstream examples use a different interface. [Pinned API source](https://github.com/shtorm-7/sing-box-extended/tree/a47bdbe2aefc4da0aa8dd2280fb54c429dd0bfe0/experimental/libbox), [official Apple client](https://github.com/SagerNet/sing-box-for-apple).

The adapter implements the pinned platform and command handler protocols. It maps dual-stack addresses/routes/DNS into NetworkExtension settings, returns the actual utun fd, monitors physical interfaces and supplies real interface addresses/flags/MTU. NE settings requests and teardown are serialized. A timed-out request cancels and poisons that provider instance; late completion clears settings and cannot revive a new session. The private app-group Unix command socket uses a random secret, with no fixed public TCP listener. Optional process routing and native notifications return explicit unsupported errors. Normal system certificate validation is preserved.

Libbox is linked statically into the extension executable; a dynamically embedded framework is not required. The host checks the provider identity, executable and reviewed core revision together with the readiness/development-signature gate. The native counter stream and exact session restoration are now implemented, but this is not proof of real traffic forwarding. Verify start/stop/reconnect, traffic counters and routing with signed profiles before any production readiness change.

## Local signed Debug preparation

The repository provides [MAC_DEVELOPMENT.md](MAC_DEVELOPMENT.md) and `scripts/build_apple_development.py`. Its default is a read-only preflight. `--build` requires a paid Team ID and all prerequisites, uses the native Mac architecture and Apple Development signing, and never accepts the Xcode license, enrolls/pays, creates profiles or enables automatic provisioning/device registration. Post-build verification uses `--verify-only --local-development` to preserve the signed bundle, checks both strict Apple-anchored signatures and verifies the embedded development profiles, exact capabilities, team, device and signing certificate.

The core update requires a newly built/staged framework and provenance from this selected revision and Go 1.26.8; staging from the previous core is rejected. The local setup still has unfinished Xcode first launch/license, zero valid Apple Development identities and an unprepared team/profile setup. The owner must complete Xcode first launch personally, sign in with a paid team and provision both targets in Xcode. Team ID may be shared; passwords/private keys/profiles should remain local. No local signing/build or actual VPN traffic test has been performed by this preparation workflow. The source readiness marker remains false.

## Verification and iPhone follow-up

Cross-platform validation checks the project wiring, profile identifiers, entitlements, channels and unavailable-core marker. The native controller and provider can be typechecked against the installed macOS SDK with Command Line Tools and a workspace module cache. The unsigned macOS preview workflow compiles the full Flutter host and provider on an Xcode runner; its artifact is explicitly named `macOS-ui-preview-no-VPN`. Native Settings (Command-comma) and Import Server (Command-N) forward navigation through `ru.honeyvpn.proxy/commands`; standard Close/Edit/Quit actions remain intact. The app icon uses the repository's neutral gold shield artwork, exported into every macOS AppIcon size by `scripts/generate_macos_icon.cjs`.

Before a working release, signed tests must cover permission refusal, app-group access, asynchronous provider failure, actual stop confirmation, process crash/reopen, physical-interface changes, IPv4/IPv6 and DNS routing. A successful unsigned build is not evidence of traffic forwarding or App Store acceptance.

The repository's iOS folder currently contains generated debugging helpers, not a Runner or packet provider project. iPhone support should reuse the packet-tunnel runtime and channel contract, but needs an actual iOS host, extension target, device provisioning and App Store/TestFlight validation. Per-app VPN on iOS is restricted to managed devices; a consumer switch must not promise unrestricted app selection. [Apple TN3134](https://developer.apple.com/documentation/technotes/tn3134-network-extension-provider-deployment).
